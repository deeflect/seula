# How Sieve works

Sieve reads a query against a known table schema. `featurizeQuery` tokenizes up to 24 tokens, matches field names, aliases, and enum values, and gives each token eight feature IDs. Grammar words such as `over` and `before` are encoded by fixed lexicons. The network never sees the original word spelling; this helps schema transfer, but creates collisions. For example, `topping` and `beneath` have identical features in the same context, so the model cannot learn their opposite meanings from those features alone.

The small neural network predicts token roles and clause boundaries. `compileTokens` turns them into typed filter clauses. `validateCompiledQuery` rejects unsupported or unapplied syntax; `SieveModel.parse` exposes `accepted`, `issues`, and `clauses`. `filterDatasetRows` applies accepted clauses with AND semantics. A rejection should be shown to the user, not silently treated as an empty or partial filter. For imported rows, `normalizeImportedRow` converts values to the schema types first.

The model is genuinely trained, but the rule system does much of the work: schema matching, operator lexicons, value cleanup, compiler, and guard. The frozen 100-case [challenge](experiment-results.md) compares raw neural roles, guarded parsing, and heuristic roles through the same compiler. On the initial core it accepted 25 of 90 valid phrases with 22 exact ASTs; after a compiler fix prompted by those results, it accepted 26 with 26 exact ASTs. Both runs rejected all 10 expected-invalid phrases. The second run is development feedback, not a fresh held-out validation. These agent-authored cases do not estimate natural-language accuracy.

The five stored PyTorch/TypeScript parity traces demonstrate numerical agreement within the test tolerances, not bit-exact behavior on all inputs. The weight edit uses four calibration phrases; the original retention check covered five stored traces. That is not evidence of zero forgetting. A separate [vocabulary experiment](vocabulary-results.json) shows that unknown comparator words remain rejected after the edit, and matched supervision cannot overcome a feature collision.

A Headless Chrome 152 browser check exercised six CPU/WebGPU queries. It reported WebGPU as the backend, identical compiled clauses, and maximum logit difference `0.000011` for that batch; rejected syntax kept its issues. One 1,024-query browser run printed 147.1 ms GPU versus 227.9 ms CPU, but the implementation also ran the CPU comparison first, so that is not an end-to-end app speedup claim. Browser checks also covered imported uppercase JSON columns, string-encoded numbers and booleans, visible malformed-JSON errors, and escaped text content.

The architecture and problem setting have antecedents in [gpu-query](https://github.com/safzanpirani/gpu-query). Direct model edits have prior art in [ROME](https://arxiv.org/abs/2202.05262) and [Weight-Space Programming](https://rikiyat.github.io/blog/weight-space-programming/); Sieve's head perturbation is a different, small supervised experiment, not a reproduction of those methods. Rejection must be evaluated with both risk and coverage, as in [selective classification](https://papers.neurips.cc/paper/7073-selective-classification-for-deep-neural-networks.pdf). [Compositional Generalization in Semantic Parsing](https://arxiv.org/abs/2007.08970) studies new combinations of known elements in semantic parsing; that question is distinct from Sieve's schema transfer and does not support a Sieve performance claim.
